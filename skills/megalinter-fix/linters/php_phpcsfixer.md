## Fix instructions

php-cs-fixer is a formatter: it enforces PHP coding standards (PSR-12, PER-CS, Symfony, custom rule sets)
and can rewrite the code itself. MegaLinter runs it in check mode, so reported problems are style
deviations that the tool can fix automatically.

- Run the tool's own fix command locally to repair all reported files: `php-cs-fixer fix` (or `php php-cs-fixer.phar fix path/to/code`). It applies the rules from the project configuration file.
- Preview changes without writing them: `php-cs-fixer fix --dry-run --diff` — this shows the unified diff of what would be fixed; apply it by re-running without `--dry-run`.
- Restrict a run to specific rules if needed: `php-cs-fixer fix . --rules=line_ending,full_opening_tag`, or pass rule options as JSON: `--rules='{"concat_space": {"spacing": "none"}}'`.
- Interpret exit codes when the run fails: `4` means invalid PHP syntax in a scanned file (fix the syntax error first), `8` means files still need fixing, `16`/`32` mean the configuration or a fixer configuration is invalid — repair the config file rather than the code.
- Only fall back to manual edits when auto-fixing is undesirable (e.g. a diff too large to review); the diff output tells you exactly what to change.

## Inline disable

Use the `@php-cs-fixer-ignore` annotation in any comment of the file. It disables the listed rules for
the **entire file** (there is no per-line suppression) and can carry an optional justification. The
feature is experimental and may change in minor releases.

```php
<?php
// @php-cs-fixer-ignore no_useless_else Justification: legacy control flow kept as-is

/*
 * @php-cs-fixer-ignore no_unset_on_property,no_binary_string
 */
```

## Ignore via configuration

The configuration file must return a `PhpCsFixer\Config` instance: disable a rule by setting it to
`false` in `setRules()`, and exclude paths through the `Finder` (`exclude` works only for directories;
use `notPath` for single files). There is no separate ignore file.

```php
<?php
$finder = (new PhpCsFixer\Finder())
    ->in(__DIR__)
    ->exclude(['autogenerated_content', 'tests/fixtures'])
    ->notPath(['src/legacy_file.php']);

return (new PhpCsFixer\Config())
    ->setRules([
        '@PSR12' => true,
        'align_multiline_comment' => false, // rule from the set, disabled
    ])
    ->setFinder($finder);
```

## When disabling is legitimate

- Generated or vendored PHP (scaffolded CRUD, compiled templates, imported SDK code) that would be rewritten on the next generation — exclude the directory in the Finder instead of fixing it.
- A rule from an enabled set (e.g. `@PhpCsFixer`) that conflicts with a deliberate team convention — set that single rule to `false` rather than dropping the whole set.
- Legacy files where the auto-fix diff would be huge and obscure real changes in review — file-level `@php-cs-fixer-ignore` or `notPath` until the file is refactored.
- Experimental inline ignores breaking after an upgrade (the annotation API is experimental) — prefer configuration-level exclusions for long-lived suppressions.
- Disabling at the MegaLinter level (`DISABLE_LINTERS`, `PHP_PHPCSFIXER_DISABLE_ERRORS`, `PHP_PHPCSFIXER_FILTER_REGEX_EXCLUDE`) is the last resort, only when the tool itself cannot be configured to behave as needed.
